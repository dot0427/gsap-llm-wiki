# 反思

## 哪一個節點最常出錯？
**⑧ 生成 HTML 簡報。**
Wiki 本身的錯（缺來源標記）lint 都抓得到，但生成簡報時 LLM 為了「講得更好懂」，會自己補一句 Wiki 沒有的解釋（第 11 頁 scrub＝progress() 那句）。這種錯最危險：看起來很合理、字面上的 API 也都存在，所以自動檢查抓不到。

第二常出錯的是 ④ 更新概念頁：只在標題標 [S2]，底下每行沒標，lint 一次抓出 13 行。

## 把檢查往前移到哪一步？
1. **把「claim 對應」從生成之後，移到生成之前（新增節點 ⑦）**：先列出每頁要講的句子、各自對到 Wiki 哪一行，對不到的句子不准進簡報；真的需要就先回去補 Wiki（附來源），再生成。這樣「自己推論」在寫 HTML 前就被擋下，而不是等看截圖才發現。
2. **把「行內標 [S#]」從 lint 移到 ingest 當下**：寫概念頁時每寫一行就標來源，不要等 lint 再一次補 13 行。

## 有沒有因此修改 workflow / graph？為什麼？
有，從 v1 改成 v2：
- 新增 ⑦「大綱＋claim 對應」節點，和「對不到 → 回 ⑥ Query 或補 Wiki」的回圈
- ④ 的規則改成「每行都要標 [S#]」，寫進 CLAUDE.md
- lint 規則修掉誤判（討論紀錄裡寫「沒講 gsap.set()」不算事實）

原因：**越晚發現錯誤，修的成本越高。** 簡報寫完才發現某句沒根據，要改 HTML、重跑檢查、重看截圖；在大綱階段擋掉只要刪一行字。而且自動檢查只能比對「字」不能比對「意思」，所以要靠流程設計，讓「意思」在更早、更好檢查的階段（一句話對一行 Wiki）就先對過。
